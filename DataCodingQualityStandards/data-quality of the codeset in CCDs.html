Code Quality: National Standards vs Local Codes

For elements where we expect national coding standards (labs, procedures, diagnoses, medications), how often is the data actually coded to a recognized standard — and how often is it local or proprietary? Measured per source using 200 CCDs each.

← Back to Explore

Question

CCD clinical entries are supposed to carry nationally recognized codes: LOINC for labs, CPT/SNOMED for procedures, ICD-10/SNOMED-CT for diagnoses, RxNorm/NDC for medications. In reality, many source systems send local, proprietary, or facility-specific codes instead — sometimes with a standard code alongside, sometimes exclusively.

For each source, what percentage of coded elements use a national standard vs. a local code? This directly determines how much mapping or tolerance logic is needed when building Silver tables.

Why This Matters

  • Silver parsing complexity: Sources that are well-coded to national standards can be parsed with generic rules. Sources heavy on local codes need custom mapping tables or fallback logic — which is expensive to build and maintain.
  • Interoperability assessment: A source sending 90% local codes is effectively non-interoperable at the coded level, even if the XML structure is valid C-CDA.
  • Prioritization: Knowing which sources are well-coded helps prioritize which ones to onboard first to Silver — quick wins vs. heavy lifts.
  • Vendor conversations: Data showing "your lab results are 80% local codes" is a concrete artifact for requesting better coding from a source system.

What Counts as "Standard" vs "Local"

The classification is based on the codeSystem OID attached to each coded element in the CCD. Recognized national code system OIDs:

Code System OID Expected In
LOINC 2.16.840.1.113883.6.1 Labs (Results), Vital Signs
SNOMED-CT 2.16.840.1.113883.6.96 Problems, Procedures, Allergies
ICD-10-CM 2.16.840.1.113883.6.90 Problems, Encounter Diagnoses
CPT-4 2.16.840.1.113883.6.12 Procedures
HCPCS 2.16.840.1.113883.6.285 Procedures, DME
RxNorm 2.16.840.1.113883.6.88 Medications
NDC 2.16.840.1.113883.6.69 Medications
CVX 2.16.840.1.113883.12.292 Immunizations

Classification logic per coded element

  • Standard — The code/@codeSystem matches a recognized national OID from the table above.
  • Local — The code/@codeSystem is present but does not match any recognized national OID. This includes facility OIDs, vendor-internal OIDs, and unregistered code systems.
  • Missing — No code element, or code element present but @code or @codeSystem is empty/absent. The element relies solely on originalText or translation elements.
Translation elements: Some sources put a local code as the primary and a standard code in a <translation> element (or vice versa). The exploration checks both and classifies an element as "Standard" if any code in the entry (primary or translation) carries a national OID. This gives sources credit for providing a standard code even if it's not the primary.

20 documents per source is sufficient for an initial pass because coding practices are a property of the source system configuration, not individual patient records. If a source sends local LOINC codes for labs, it does so consistently across all patients. Run multiple batches (leveraging the restart capability) if you need higher statistical confidence.

Workflow

1
List all Assigning Authorities — pull distinct source identifiers from the FHIR Document Reference index or S3 inventory for the target period.
2
Sample 20 CCDs per source — randomly select from documents received in the window. If a source contributed fewer than 20 docs, use all available and note reduced sample size. Run additional batches using restart capability if more confidence needed.
3
Parse and extract coded elements — for each CCD, walk the clinical sections (labs, procedures, problems, medications, immunizations, encounters). For each entry, extract the primary code/@code, code/@codeSystem, and any translation elements.
4
Classify each coded element — compare the codeSystem OID against the known national standards list. Tag each as Standard, Local, or Missing. If a translation element carries a standard code, promote the element to Standard.
5
Aggregate by source and domain — for each Assigning Authority, compute: total coded elements, % standard, % local, % missing — broken down by clinical domain (labs, procedures, problems, medications, immunizations, encounters).
6
Identify the local code systems — for elements classified as "local", collect the distinct OIDs used. Report the most common local OIDs per source — these are the systems that would need mapping tables if you want to normalize.
7
Output report — one row per source with overall and per-domain code quality scores. Rank sources from best-coded to worst-coded.

Common Patterns You'll See

Pattern 1: Well-coded source (EPIC, large academic centers)

90%+ standard codes across all domains. Local codes are rare and usually limited to internal order identifiers that supplement (not replace) the LOINC/SNOMED code.

Pattern 2: Partially coded (Cerner, some community hospitals)

Problems and medications are reasonably well-coded (70-85% standard), but labs carry local order codes as the primary identifier. LOINC may appear in a translation element or not at all.

Pattern 3: Heavily local (older MEDITECH, small practices, some interfaces)

50%+ local codes, especially in labs and procedures. The source system stores internal codes and the interface engine doesn't map them. Sometimes the originalText has a readable name but no standard code.

Pattern 4: Missing codes (interface engine artifacts)

High "missing" rates often indicate a middleware or interface engine that strips or fails to populate the code element. The data may exist in the source EHR but isn't making it into the CCD.

Labs are typically the worst. Lab ordering systems often use local catalog numbers (e.g., "LAB1234") as the primary code. LOINC mapping is maintained separately and not always applied to the outbound CCD. Procedures and problems tend to be better because ICD-10 and CPT are required for billing and therefore already present in the source system.

Interpreting Results

Standard % Assessment Implication for Silver
≥90% Well-coded Generic parsing rules work. Minimal custom mapping needed. Good candidate for early Silver onboarding.
60–89% Mixed Standard codes available for most elements but local codes appear in specific domains (often labs). Will need per-domain mapping tables for the local portion.
<60% Heavily local Majority of coded data uses proprietary identifiers. Parsing requires extensive mapping tables or tolerance for unresolved codes. Higher cost to onboard to Silver.
High missing % Structural gap Data may exist in the source but isn't flowing into CCDs. Investigate whether the interface configuration can be improved before building workarounds.

Run It

Use the exploration utility against sampled CCDs from S3:

python Utilities/explore_code_quality.py \
  --s3-bucket your-raw-bucket \
  --prefix ccds/ \
  --docs-per-source 20 \
  --window-days 14 \
  --output code_quality_report.json

Or against a local directory of pre-downloaded samples:

python Utilities/explore_code_quality.py \
  --local-dir ./sampled_ccds/ \
  --docs-per-source 20 \
  --output code_quality_report.json
The script supports restart: if interrupted, re-run and it skips already-processed files. Results flush to disk every 200 records. Run multiple times to accumulate more samples per source. The script also produces a local_oid_inventory.csv listing every distinct local OID found, the source it came from, the domain, and a sample code value and displayName — useful for starting a mapping table.

Edge Cases

  • Section Absent vs Missing Data: A source might not include a section at all (e.g., a mental health provider with no lab section) — this is "Section Absent" and may be legitimate. This is different from "Missing Data" where the section exists but coded elements within it are empty or unusable. Both are tracked separately.
  • NullFlavor codes: Some entries carry a nullFlavor attribute instead of a code (e.g., nullFlavor="UNK"). These are classified as "Missing" — the source acknowledged the element but couldn't code it.
  • Deprecated OIDs: Older ICD-9 codes (OID 2.16.840.1.113883.6.103) are technically a recognized code system but are outdated. The report flags them separately as "Standard (legacy)" so you can see how much historical data hasn't been updated.
  • Free-text only entries: Some entries have only originalText and no code element at all. Classified as "Missing" but noted separately — these may be unstructured notes embedded in structured sections.
  • Multiple codes per entry: A single observation may carry a primary code + multiple translations. The exploration counts this as one element and gives it the "best" classification (Standard > Local > Missing).
