EPIC Source Detection Explore

Classify each data source contributing CCDs as "EPIC", "Not-EPIC", or "NOT SURE" using structural fingerprints from just 100 documents per source over a 1-week window. This supports a service where we deliver data from non-EPIC sources to EPIC hospitals.

← Back to Explore

Question

We deliver clinical data from non-EPIC sources to EPIC hospitals. To understand what we're working with, we need to tag every contributing source as EPIC, Not-EPIC, or NOT SURE — using only the CCD content itself (no vendor contracts or external metadata).

Constraint: Use only 100 CCDs per Assigning Authority, sampled from a single recent 7-day window.

Why This Matters

  • Routing logic: If a source is already EPIC, its data may be redundant for EPIC destination hospitals — or may need different deduplication handling.
  • Transformation rules: EPIC CCDs have known structural patterns that can be exploited for faster, more reliable parsing. Non-EPIC sources need broader tolerance.
  • Quality baselines: Knowing vendor lineage lets you benchmark data quality expectations per source without relying on incomplete metadata.
  • Contract validation: Cross-reference the data-derived classification against what vendors claim — discrepancies flag configuration issues or gateway artifacts.

Fingerprint Signals in the CCD

EPIC-originated CCDs carry distinctive structural signatures that differentiate them from Cerner, MEDITECH, Allscripts, eClinicalWorks, and other systems. The key signals:

Signal Where in CCD EPIC Indicator
Root templateId OIDs ClinicalDocument/templateId EPIC uses specific OID combinations for CCD, CCD-A, and referral documents
Custodian / Author software assignedAuthoringDevice/softwareName or custodian/assignedCustodian Often contains "Epic" or "EpicCare" in the software name field
Section ordering Order of component/section elements EPIC follows a predictable section sequence (allergies → meds → problems → results…)
Extension namespace patterns id/@root OIDs across entries EPIC-internal OID patterns (e.g., 1.2.840.114350.x.x.x family)
Entry formatting style Whitespace, attribute ordering in observations EPIC serializers produce consistent indentation and attribute order
Participant / performer patterns performer/assignedEntity EPIC encodes provider NPI and org hierarchy in a distinctive nested pattern
Important: No single signal is definitive. The classification uses a weighted score across all signals. A source scoring high on 4+ signals is tagged EPIC with high confidence; a source with only 1-2 weak matches goes to NOT SURE.

Sampling Strategy

Documents per Source
100 CCDs (randomly sampled)
Time Window
7 consecutive days (recent)
Grouping Key
Assigning Authority (source system)
Minimum for Classification
At least 80 of 100 docs must agree

100 documents is sufficient because EPIC's structural patterns are generated by the software, not the clinical content. If a source is running EPIC, virtually every CCD it produces carries the same fingerprints regardless of which patient or encounter it describes.

Workflow

1
List all Assigning Authorities — pull distinct source identifiers from the FHIR Document Reference index or S3 inventory for the target week.
2
Sample 100 CCDs per source — randomly select from documents received in the 7-day window. If a source contributed fewer than 100 docs that week, use all available and note reduced confidence.
3
Extract fingerprints — for each CCD, parse the XML and collect: root templateId OIDs, software name strings, section LOINC codes in order, OID families used in entry IDs, and namespace patterns.
4
Score against profiles — compare each document's fingerprints to a known EPIC reference profile (and optionally known Cerner / MEDITECH profiles). Each document gets an EPIC confidence score (0–100).
5
Classify the source — aggregate scores across the 100 documents:
  • ≥80 docs score above EPIC threshold → EPIC
  • ≥80 docs score below EPIC threshold AND match a non-EPIC profile → Not-EPIC
  • Otherwise → NOT SURE
6
Output a classification table — one row per Assigning Authority with the tag, confidence score, sample size, and the top contributing signal.

Known EPIC Signature Reference

These patterns are consistent across EPIC deployments seen in NY SHIN-NY feeds:

Signal Pattern Weight
Software name Contains "Epic" (case-insensitive) in softwareName or manufacturerModelName High (0.35)
OID family Root IDs starting with 1.2.840.114350 High (0.30)
Section order Allergies → Medications → Problems → Results → Vital Signs → Procedures Medium (0.15)
templateId set Includes 2.16.840.1.113883.10.20.22.1.2 (CCD) with EPIC-specific companion templates Medium (0.10)
Formatting style Consistent 2-space indentation, attributes alphabetically ordered Low (0.10)
These weights are starting points. After initial classification, validate against known ground truth (sources where you know the vendor) and adjust weights accordingly.

Edge Cases & NOT SURE Scenarios

  • HIE gateways: Some sources route through an HIE that rewrites headers. The CCD may lose its original software name while retaining internal OID patterns — producing mixed signals.
  • Epic Community Connect: Smaller practices on a host hospital's EPIC instance may use the host's OIDs but with slightly different templates. These usually still classify as EPIC.
  • Recent migrations: A source that recently switched from Cerner to EPIC may have a mix of old and new documents in the same week. The 80/100 threshold catches this as NOT SURE.
  • White-label / interface engines: Some organizations use Rhapsody or Mirth to transform outbound CCDs, stripping original vendor markers. These are genuinely ambiguous.

Run It

Use the exploration utility against a set of sampled CCDs (from S3 or local export):

python Utilities/explore_epic_source_detection.py \
  --s3-bucket your-raw-bucket \
  --prefix ccds/ \
  --window-days 7 \
  --docs-per-source 100 \
  --output epic_classification_report.json

Or against a local directory of pre-downloaded samples:

python Utilities/explore_epic_source_detection.py \
  --local-dir ./sampled_ccds/ \
  --docs-per-source 100 \
  --output epic_classification_report.json

Interpreting Results

EPIC
Source is almost certainly running Epic EHR. Data destined for EPIC hospitals may already exist there — check for deduplication needs.
Not-EPIC
Source runs a different EHR (Cerner, MEDITECH, Allscripts, etc.). This is the data we're primarily delivering to EPIC hospitals — highest value for the service.
NOT SURE
Ambiguous signals. May need manual investigation, a larger sample, or cross-referencing with provider directories to resolve.
